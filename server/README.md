# DOTNXS Render server

`cpp_server.cpp` is the public C++ HTTP gateway. It provides `/ping` (`pong`) and `/health`, and forwards `/v1/chat` to the private Python worker in `worker.py`. The Python worker retains the official Transformers model math; the gateway does not pretend to be a C++ Inkling inference engine.

## Manual Render setup

1. Create a **Static Site** from `RMAAPK/DOTNXS`, Root Directory `website`, build command `npm install && npm run build`, and Publish Directory `build`. The Vite output is configured to match the existing Render service setting. Add custom domain `dotnxs.rmaa.pk` and configure the DNS record Render provides.
2. Create a **Web Service** from the same repository, runtime **Docker**, Root Directory `server`, Dockerfile path `./Dockerfile`, and Docker Context `.` (the `server/` directory). The Dockerfile fetches/builds the `dotnxs` wheel from GitHub, so it works with this monorepo root setting. The image starts the C++ gateway and its local Python inference worker.
3. The current Render API URL is `https://dotnxs-server.onrender.com` (service `DOTNXS-Server`); it is set in `website/public/config.js`. If Render assigns a different service URL, update that file and redeploy the static site.
4. Set the service environment variables if needed: `NXS_REPO_ID`, `NXS_FILENAME`, `DOTNXS_CACHE_BYTES`, `DOTNXS_STORAGE_CACHE_BYTES`, `DOTNXS_STORAGE_CACHE_RESERVE_BYTES`, `DOTNXS_STORAGE_CACHE_DIR`, `DOTNXS_MAX_CONTEXT_TOKENS`, `DOTNXS_MAX_NEW_TOKENS`, and `CORS_ORIGINS`. Defaults are set for the public NXS repo, a 16 MiB RAM chunk cache, and up to 5 GiB of temporary file-backed tensor storage.

Render's service Root Directory is `server/`, so commits that only change `dotnxs/` do not trigger its auto-deploy. The Docker build fetches `dotnxs` from GitHub `main`; redeploy the API after runtime-only package changes.

The C++ service has `/ping`, which returns `pong` without initializing the model. Render Free sleeps after 15 idle minutes. `website/public/ping.html` can ping every ten minutes while open; for a background heartbeat, set the GitHub repository variable `RENDER_PING_URL` to `https://dotnxs-server.onrender.com/ping`. The scheduled GitHub Actions workflow calls it every ten minutes. This avoids ten separate Render Cron services, each of which has a minimum charge. The static-site client fetches the public tokenizer files from the exact Hugging Face revision reported by `/health` and performs prompt tokenization and output decoding in the browser. The server worker does not instantiate a tokenizer; `/v1/chat` accepts `input_ids` and streams generated token IDs.

## Free-plan limits

Render's Free web service has 512 MB RAM and spins down after 15 minutes without inbound traffic. The heartbeat can keep it awake, but it consumes the workspace's monthly Free instance hours (750 hours total) and does not bypass that limit. Dense tensors are now mapped from temporary files rather than copied into ordinary Torch buffers; the current model's non-expert layer tensors total about 1.27 GiB on disk and fit within the configured storage-cache cap. File-backed pages still count as memory while resident, so Free-plan fit is not yet verified. The temporary filesystem cache is lost on restart or spin-down, and Render can evict instances when ephemeral storage is exceeded. Full token generation can still require several GB of streamed expert weights and substantial network traffic. Ping does not remove RAM, disk, CPU, or bandwidth limits. Render's 2 CPU / 4 GB `2c-4g` plan is paid.

The API serializes generation, caps prompts at 64 tokens and replies at 12 tokens, and is text-only. Inkling executes 48 layer applications per token, so CPU response latency can be high. Dense layer tensors use `torch.from_file` over verified NXS-entry files; selected NVFP4/MXFP8 experts use Numba JIT matvecs directly over mapped packed-weight files, avoiding full float32 expert matrices. The RAM chunk LRU is 16 MiB and the temporary file cache is capped at 5 GiB (or less if free disk is lower). The browser handles tokenization. This is an incremental storage-backed path, not a completed low-memory inference validation; the native C++ model engine remains unfinished. The public NXS repo does not require `HF_TOKEN`; if you add one for a private repo, set it as a Render secret, not in source.
